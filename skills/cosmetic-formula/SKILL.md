# cosmetic-formula

기획이 말하는 느낌을 랩이 만들 수 있는 요구로 바꾼다. 이 스킬은 처방을 짜지 않는다.
**무엇을 원하고, 어디서 출발하고, 무엇으로 확인할지**를 적어 랩에 넘긴다.

사용자가 `/cosmetic-formula` 뒤에 쓴 것: `$ARGUMENTS`

## 공통 규칙 (모든 cosmetic-* 스킬)

- 작업 폴더는 `cosmetic/<프로젝트-슬러그>/`다. 어느 프로젝트인지 확인한다.
- 사실이 아닌 것을 만들지 않는다. 추정은 '가설', 모르는 것은 '확인 필요'. 숫자는
  출처와 확인일.
- 경쟁사 문구를 베끼지 않는다. 효능, 1위, 근거 없는 수치를 만들지 않는다.
- beauty-data MCP는 있으면 쓰고 없으면 공개 자료와 랩 문의로 내려간다. MCP 데이터(카피
  원문, OCR, 처방, 공급사, 가격)는 내부용이고 외부 게시물에 옮기지 않는다.

## 이 스킬만의 규칙

- **처방 수치(wt%), 공급사·제조사 이름, 원료 단가는 문서에 옮기지 않는다.** 제품 코드,
  원료 코드, 조회한 도구 이름과 as_of만 적는다. 랩은 같은 원천을 직접 본다.
- 처방이 되는지, 안정한지, 점도·pH가 얼마일지는 **'랩 확인 필요'**. 기능성 보고·심사,
  사용 한도, 표시 의무는 **'RA 확인 필요'**. 짐작해서 채우지 않는다.
- 성분이 들어 있다고 완제품 효능이 증명되지 않는다. 규격(standard)은 LOT 실측이 아니다.
  비어 있는 값(null)은 '모름'이다.

## Step 1: 읽기

`brief.md`(무엇을 만들고 싶나), `competitors.md`/`competitors.csv`(경쟁 전성분과 무엇으로
파나), `numbers.json`(내용물 원/g 목표), `claims.csv`(기능성·효능 목표가 있으면),
`panel/results.md`(사용감·향 관련 반대 이유). 없는 파일은 없다고 적고 진행한다.

## Step 2: 출발 처방 찾기

### beauty-data MCP가 있을 때

1. `riselab_search_products`로 같은 카테고리·비슷한 컨셉의 사내 제품을 이름이나 코드로
   찾는다. 상태(active/inactive)를 적는다. 부분 일치는 자동으로 고르지 않는다.
2. 후보마다 `riselab_get_product_knowledge`(정확한 코드)로 규격(pH, 점도, 비중), 처방 골격,
   공정을 본다. BOM 버전이 여럿이면 `bom_version`을 골라야 한다.
3. 맞는 제품이 없으면 `riselab_base_formulas`(베이스 처방)에서 출발점을 찾는다.
4. 문서에는 이렇게 적는다: "출발점: <코드> <제품명> (active, riselab_get_product_knowledge,
   as_of YYYY-MM-DD). 주계면 계열: ..., SLS·SLES 없음. 수치는 원천 참조." 처방 %는 적지 않는다.

### MCP가 없을 때

출발점을 "랩 추천 요청"으로 둔다. 원하는 성상, 피하고 싶은 성분, 참고할 경쟁 제품(공개
전성분)을 적어 랩이 사내 처방에서 고르게 한다.

## Step 3: 무엇을 바꾸나

출발 처방에서 바꿀 것을 표로: 뺄 것, 더할 것, 바꿀 것(향, 색, 기능 원료), 이유. 각 줄에
'가설' 또는 '확정(누가, 언제)'.

## Step 4: 컨셉 원료와 성분 리서치

`cosmetic/<슬러그>/ingredients.md`:

- 컨셉 원료 후보(이야기를 만드는 원료)와 기능 원료(기능성 고시 성분 등)를 나눈다.
- MCP가 있으면 `riselab_materials`(성분명이나 INCI 목록)로 **사내 보유 여부와 원료 코드**를,
  `riselab_material`로 구성 성분을 본다. 없으면 `needs_sourcing`으로 표시한다.
- 시장에서 어떻게 쓰이나: `oy_ingredient_claims`, `market_summary`, `get_ingredient`,
  `search_ingredients`. 카피는 요약만, 원문은 옮기지 않는다.
- MCP가 없으면 INCI 명칭과 기능은 공개 자료(EU CosIng, 대한화장품협회 성분사전)에서 링크와 함께.
- 근거(논문, 원료사 자료)는 링크로. 원료사 자료는 원료사 주장이라고 적는다.
- 효능 표기를 할지는 여기서 정하지 않는다. 표현은 `/cosmetic-claims`가 본다.
- "N가지 추출물"처럼 개수를 세어 파는 방식은 피한다(근거 없는 숫자 표현이 되기 쉽다).

## Step 5: 목표 원가

`numbers.json`의 `unit_cost.content.won_per_g`를 목표 내용물 원가로 적는다. 없으면 사용자에게
묻는다. 컨셉 원료의 함량·단가로 원/g이 맞는지는 **랩 견적 확인 필요**. 원료 단가를 추정해
계산하지 않는다.

## Step 6: 성상·사용감 목표

| 항목 | 목표 | 상태 |
| --- | --- | --- |
| 성상·색 | 예: 무색 투명 젤 | 가설 |
| 점도 | 용기·펌프 토출에 맞게 | 랩 확인 필요 |
| pH | 카테고리 관행 범위 | 랩 확인 필요 |
| 거품·헹굼·마무리 | 예: 부드러운 거품, 당김 적음 | 가설 |
| 향 | 향 브리프(조향 의뢰) 링크 | 확인 필요 |
| 피해야 할 것 | 예: 쿨링감, 특정 계면활성제 | 확정/가설 |

## Step 7: 시험 항목

랩과 RA가 확정할 목록으로 적는다. 기간·조건·기준값은 랩이 정한다.

- 사용감 평가: 거품량, 거품 질감, 헹굼, 헹군 뒤 당김, 잔향, 향 발산(사내 패널, 평가 척도)
- 안정성: 온도 조건별 성상·색·향·점도·pH 변화 (랩 확인 필요)
- 용기 적합성: 펌프 토출량, 막힘, 용기 재질과의 상용성, 충진량 여유
- 방부력(미생물 챌린지) (랩 확인 필요)
- 기능성 목표가 있으면: 기능성 원료와 함량, 보고·심사 경로 (RA 확인 필요)
- 광고에 쓸 시험(저자극, 인체적용시험, 지속 시간)이 있으면: 무엇을 주장하려는지와 시험
  설계를 cosmetic-claims와 맞춘다. 시험 전에는 그 표현을 쓰지 않는다.
- 향료 알러젠 표시 대상 여부 (RA 확인 필요)

## Step 8: formula.md 쓰기

`cosmetic/<슬러그>/formula.md` (맨 위에 "내부용"):

1. 한 줄 요약: 무엇을, 어디서 출발해, 무엇을 바꿔 만드나.
2. 출발점 (Step 2) 과 바꿀 것 (Step 3).
3. 목표 원가 (Step 5).
4. 성상·사용감 목표 (Step 6).
5. 시험 항목 (Step 7).
6. 랩 확인 필요 / RA 확인 필요 목록: 번호, 질문, 누가.

`/cosmetic-plan`이 이 파일과 `ingredients.md`, `claims.md`, `design-brief.md`를 묶어 개발
의뢰서(`dev-request.md`)를 만든다.

## 출력

`cosmetic/<슬러그>/formula.md`, `cosmetic/<슬러그>/ingredients.md`. 다음: `/cosmetic-claims`가
기능성·효능 표현을, `/cosmetic-cfo`가 원가를 맞춘다.
